# Financial-provider candidates and reusable logo library

Status: **User-supplied product direction with approved group mapping and
unresolved provider normalization**

As of: **2026-08-22**

Authority: **Authoritative for the requirement to make the supplied provider
candidates available through an Admin-managed, reusable logo library and
product/provider configuration, and for the approved Group A through G product
mapping. The spellings, duplicate handling, canonical legal identities, and
offer-level segmentation remain raw input pending explicit normalization.**

## 1. Supplied direction

The user requires:

1. a reusable Admin media library containing the lender/provider logos needed
   for Financial Services;
2. an easy way for Admin to select those providers and logos while configuring
   financial products;
3. provider logos to support clear public comparison and enquiry/application
   journeys; and
4. no redirects from Dhanadhara to external lender websites.

The supplied names include banks, small-finance banks, housing-finance
companies, NBFCs, fintech brands, and apparent product-specific variants. A
brand and its finance or housing subsidiary must not be merged merely because
their display names are similar.

## 4. Reconciliation at ingestion time

The following observations describe the repository when this material was
first ingested. Section 7 records the later implementation; these source-time
notes are retained rather than silently rewritten.

- apps/api/app/models/loan.py defines Bank with name, optional logo_key, and
  active, but no canonical legal name, provider kind, logo asset relation,
  provenance, or public-display metadata.
- apps/api/app/services/loan_config.py supports Admin bank CRUD and rejects
  case-insensitive duplicate names. It accepts logo_key as a string; there is
  no managed logo picker, presign/confirm lifecycle, or ownership validation.
- BankLoanTypeAvailability uses a permissive default: a missing row means the
  bank is available. The supplied product-specific lists cannot be imported
  safely under that rule because an unconfigured provider would appear
  available for every product.
- Existing managed upload flows accept JPEG, PNG, and WebP. Banner tests
  explicitly reject image/svg+xml, and the shared storage sniffer does not
  recognize or sanitize SVG. Raw SVG upload must therefore not be added by
  merely extending a MIME allowlist.
- The current public Financial Services page is driven by a code-owned product
  registry, while the authenticated application catalogue is Admin-managed.
  The planned public catalogue must reconcile those sources before logo/provider
  configuration can be authoritative.

## 5. Planning constraints

1. Keep canonical provider identity separate from product-specific offer labels
   such as “- HL”, “- LAP”, “Domestic”, or “International”.
2. Preserve distinct legal entities and subsidiaries until Admin explicitly
   links or aliases them.
3. Publicly display only active providers attached through an explicit,
   published product-provider record. Never infer public availability from a
   missing operational availability row.
4. Store logo attribution/provenance and last-verified metadata. Obtain brand
   assets from official sources or a user-provided licensed asset; do not
   generate or redraw financial institution logos.
5. Use a neutral initials fallback when a verified logo is unavailable.
6. Keep every public Apply, Request Quote, and Enquire action inside
   Dhanadhara. No provider destination URL or external redirect is part of the
   catalogue.
7. Treat uploaded SVG as active content. Prefer pre-reviewed SVG assets plus
   raster-only Admin uploads unless a strict server-side SVG sanitization and
   canonicalization pipeline is separately approved and tested.

## 7. Implementation update (2026-08-22)

- The public Financial Services catalogue now derives from the Admin-managed
  Financial Products source and requires explicit product publication.
- Explicit product/provider offer rows control public provider display; the
  operational availability matrix is not used as a publication default.
- Provider records now retain legal name, provider type, logo provenance, and
  verification time. Admin can upload JPEG, PNG, or WebP logos through private
  staging, malware checks, canonicalization, and managed public storage.
- Raw SVG upload remains disabled. Repository SVGs require an exact reviewed
  manifest entry in the same change as the asset; that manifest is intentionally
  empty until canonical identity and brand provenance are approved.
- Public catalogue/detail pages use neutral initials when no verified logo is
  available. Search, filters, sorting, and pagination are internal to
  Dhanadhara, and provider offers contain no external destination field.
- Provider selection is retained only as a non-binding immutable snapshot on
  an internal application or enquiry. It does not assign the operational bank.
- The raw Groups A-G remain unseeded. Canonical identity, Group E segmentation,
  and the incomplete Group G entry are still unresolved.
- The prior upload-versus-picker decision is resolved as a hybrid: managed
  raster upload for Admin plus code-reviewed repository SVG assets.
